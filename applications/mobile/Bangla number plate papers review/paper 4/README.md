> **Project:** Re-implementation and evaluation of *“YOLOv10: Real-Time End-to-End Object Detection”* (Paper #27, arXiv:2405.14458)

This package documents a controlled project-level comparison of **YOLOv10-N, YOLOv10-S, YOLOv8-N and YOLOv8-S** for detecting Bangla BRTA licence plates, plus an additional comparison of **YOLOv10-N and YOLOv8-N as character detectors**. The notebook records training, test-set metrics, condition-specific results, latency measurements, environment information, logs, and code in `paper27_outputs.zip`.

**Important scope note:** this is a fine-tuning and evaluation study on the team dataset. It is not a reproduction of the paper’s original COCO experiment. All project metrics below are transcribed from the completed Paper #27 notebook output; they should be interpreted within this dataset and experimental setup.

## 3. Quick Start

### 3.1 Download the output archive

Download `paper27_outputs.zip` from the repository. Because GitHub identifies this file as a Git LFS object, use the repository’s **View raw / Download raw file** action or an authenticated Git LFS-capable client if the normal page does not provide the archive bytes.

Extract it locally:

```bash
unzip paper27_outputs.zip -d paper27_outputs
```

On Windows, use File Explorer’s **Extract All** action or PowerShell:

```powershell
Expand-Archive -Path .\paper27_outputs.zip -DestinationPath .\paper27_outputs
```

### 3.2 Install the detector dependency

The notebook pins Ultralytics:

```bash
pip install ultralytics==8.4.170
```

The notebook itself was run in a Kaggle environment with PyTorch 2.11.0+cu128 and Python 3.13.15. Installing Ultralytics alone does not guarantee that every exported format or GPU backend will work on another machine. TensorRT requires a compatible NVIDIA/CUDA/TensorRT stack; CPU ONNX evaluation requires ONNX Runtime.

### 3.3 Run plate detection with a saved checkpoint

After extracting the archive, locate the corresponding `best.pt` file under the relevant run directory. The example below assumes the YOLOv10-N checkpoint is at `paper27_outputs/runs/v10n/weights/best.pt`; adjust the path to match the extracted archive.

```python
from ultralytics import YOLO

model = YOLO("paper27_outputs/runs/v10n/weights/best.pt")
results = model.predict(
    source="image.jpg",
    imgsz=640,
    conf=0.25,
    verbose=False
)

for result in results:
    boxes = result.boxes.xyxy.cpu().numpy()
    scores = result.boxes.conf.cpu().numpy()
    classes = result.boxes.cls.cpu().numpy().astype(int)

    print("Class names:", model.names)
    print("Boxes [x1, y1, x2, y2]:", boxes)
    print("Confidence:", scores)
    print("Class IDs:", classes)
```

This is a practical inference example using the Ultralytics interface. The saved notebook metrics were produced by the notebook’s own evaluation code and configuration; this short example is not a claim that the example itself was separately benchmarked.

**Detection is not full licence-plate recognition.** The four `v10n`, `v10s`, `v8n`, and `v8s` runs detect plate bounding boxes. The `chars_v10n` and `chars_v8n` runs are a separate character-detection component used in the project’s plate-reading experiment.

### 3.4 Re-evaluate a detector

The dataset YAML generated by the notebook uses the detection directory and its train/validation/test splits. A typical evaluation call is:

```python
from ultralytics import YOLO

model = YOLO("paper27_outputs/runs/v10n/weights/best.pt")
metrics = model.val(
    data="path/to/detection_all.yaml",
    split="test",
    imgsz=640,
    batch=16
)

print("Precision:", metrics.box.mp)
print("Recall:", metrics.box.mr)
print("mAP50:", metrics.box.map50)
print("mAP50-95:", metrics.box.map)
```

`path/to/detection_all.yaml` is a placeholder: recreate it using the notebook’s `common.data_yaml("detection", "all")` helper or supply a valid YAML file for your local dataset. The dataset is not bundled inside the output archive.

## 6. How to Read These Results

- **mAP50** measures detection average precision at an IoU threshold of 0.50. **mAP50-95** averages across IoU thresholds from 0.50 to 0.95 and is generally stricter about box localisation.
- **Precision** describes the share of predicted detections that are correct; **recall** describes the share of ground-truth objects detected. A high mAP50 alone does not capture every operational error mode.
- **Small-plate recall is a key differentiator here.** YOLOv8-N reports 60%, compared with 20% for YOLOv10-N. The best model depends on whether tiny plates, latency, false alarms, model size or another requirement matters most.
- **Condition results are subset-specific.** YOLOv10-S has the highest reported mAP50 on the small-plate condition subset (96.8%), but the separately reported size-based recall is 40%. These are different calculations and should not be treated as interchangeable metrics.
- **Weather subsets are not fully real-world tests.** The notebook identifies rain and detection-fog copies as synthetic; performance on those subsets does not establish performance under all real weather, camera, motion or lighting conditions.
- **False alarms matter.** The reported false-alarm rate on plate-free photos ranges from 3.75% to 6.88%. A detector may achieve high mAP on positive test images and still produce unwanted detections on images with no plate.
- **Latency depends on the runtime.** TensorRT, PyTorch FP32, PyTorch FP16 and CPU ONNX are different execution paths. Do not compare these values without preserving the runtime, device, input size, batch size and timing method.
- **The YOLOv10 FP16 figures need verification.** They are included exactly as printed by the notebook, but are anomalously high compared with the corresponding FP32 and TensorRT results.
- **Character plate-exact accuracy is a separate outcome.** `chars_v10n` and `chars_v8n` are evaluated as part of the project’s character/plate-reading pipeline. Their percentages should not be compared directly with detector mAP.
- **One run is not a statistical study.** The notebook sets seed 42, but the available comparison does not report multiple independent seeds or confidence intervals. Small differences in rounded metrics should not be over-interpreted.

## 8. Limitations

1. **Dataset-specific results.** The evaluation uses the team dataset and a one-class plate detector. Results may not transfer to other countries’ plates, cameras, or data distributions.
2. **Fine-tuning rather than the original training protocol.** The models start from COCO-pretrained weights and are fine-tuned on the project dataset; this is not the original paper’s full COCO training experiment.
3. **Single reported run per configuration.** The comparison does not provide multi-seed means, standard deviations or confidence intervals.
4. **Training time limits.** The notebook specifies wall-time caps for each run. The planned epoch count is not, by itself, proof that every model completed every epoch; inspect the run’s `results.csv`, logs and `results.json` for exact completion.
5. **Auto-labelled training data.** Detection training combines 4,067 human-labelled and 4,507 auto-labelled images. Annotation quality can affect learned behaviour.
6. **Limited small-plate sample.** Small-object recall is sensitive to the number and distribution of small plates. Check the archived run metrics and dataset condition definitions before drawing broad conclusions.
7. **Synthetic weather.** Rain and detection-fog subsets are synthetic copies, so they do not replace testing on independently collected adverse-weather footage.
8. **Latency portability.** The reported speeds are specific to the Tesla T4, runtime versions and measurement procedure. Real deployment latency will vary with hardware, image pipeline, batch size and software stack.
9. **FP16 timing anomaly.** The reported YOLOv10 PyTorch FP16 latency values are much higher than the corresponding FP32 and TensorRT FP16 values. They must be verified before use in performance claims.
10. **Detection and recognition are different tasks.** Plate-box mAP and character/plate-exact percentages are not directly comparable. End-to-end recognition quality depends on the full detection, crop, character and decoding pipeline.
11. **No broad deployment claim.** The results do not establish reliability under all lighting, weather, occlusion, motion blur, camera, or plate-format conditions.
12. **No direct COCO benchmark reproduction.** Original-paper metrics and this study’s licence-plate metrics come from different datasets and setups.

## 9. Differences from the Original Paper

| Component | Original YOLOv10 paper | Paper #27 project experiment |
|---|---|---|
| Paper | *YOLOv10: Real-Time End-to-End Object Detection* | Project-level re-implementation/evaluation inspired by Paper #27 |
| Dataset | MS COCO (80 object classes) for the paper’s benchmark | Detection split (one class: `plate`) |
| Starting point | Original paper’s training protocol and models | COCO-pretrained Ultralytics checkpoints |
| Training schedule | Paper’s own COCO protocol | 60 planned epochs for plate detection; 70 planned for character-detector runs, with time caps |
| Models compared | YOLOv10 variants and other detector baselines in the paper | YOLOv10-N/S and YOLOv8-N/S |
| Input size | 640 for the reported model comparison | 640 for plate detection; 320 for character detection |
| Hardware | Paper’s reported benchmark setup | Kaggle with two NVIDIA Tesla T4 GPUs |
| Metrics | COCO AP and efficiency measurements under the paper’s protocol | mAP50, mAP50-95, plate counts, size/condition subsets, false alarms, latency and character/plate-exact results |
| End-to-end latency | Paper’s reported benchmark values | Project measurements using PyTorch FP32/FP16, TensorRT FP16 and CPU ONNX |
| Character-detector experiment | Not the core benchmark in the cited paper | Additional YOLOv10-N vs YOLOv8-N project experiment |

YOLOv10’s research contribution includes consistent dual assignments for NMS-free training and a holistic efficiency–accuracy-driven model design. This project compares the available YOLOv10 and YOLOv8 model implementations after fine-tuning on a separate task. The experiment does **not** isolate the contribution of each architectural component, nor does it prove that every observed difference is caused only by NMS-free design.

Paper-level COCO figures in Section 5.5 are included as context. They should not be described as directly comparable benchmark scores because dataset, training protocol, model implementation and timing environment differ.
